## 5주차 — 프론트 메인 플로우 E2E (2026-07-13)

### 문제

모델 서버를 실제 사용자가 쓸 수 있는 화면으로 연결해야 한다. 특히 OCR 교정 강제(§9-4)와
표현 수위("위험" 대신 "불리 가능성", §9-1)를 UI에서 지켜야 한다.

### 목표

업로드 → 교정 → 분석 → 결과의 메인 플로우 E2E 동작 (스펙 §3.1)

### 구현

- React 18 + Vite + react-router-dom (history 라우팅 — Capacitor v2 전제 조건 준수)
- 업로드: 이미지(base64 → /ocr) + 텍스트 직접 붙여넣기 이중 경로 (§14 OCR 열세 대비)
- 교정 화면 강제 통과, 결과 화면: 요약 카드 4종 + 위험도순 조항 카드(뱃지·확신도·
  감지 신호·uncertain 안내), 고지 문구 상시 노출
- 메인화면 서비스 소개 + 필수 특약 가이드(/guide) 정적 페이지 (§3.2)
- 모델 서버 CORS 허용 추가

### 의사결정

| 결정 | 이유 |
|---|---|
| uncertain 카드에 모델 원 판정·무료 상담(132) 안내 병기 | "확인 필요"만 보여주면 사용자가 갈 곳이 없음 (§9-2) |
| 챗봇은 v2 후보로 스펙에 조건부 기록 | 자유 판별형은 설계 원칙(§2) 충돌. 분석 결과·가이드 범위 내 Q&A만 허용하는 조건 명시 |
| 수동 테스트 오판을 오판 로그로 축적 시작 | 스펙 §5.5 재학습 루프의 데이터 수집을 UI 검증 단계부터 가동 |

### 검증

- 4종 시나리오 수동 테스트 (위험 계약서 / 모범 계약서 / 애매 계약서 / 구어체):
  위험 조항을 safe로 놓친 사례 0건. 위험 계약서 6/6 정확.
- 발견된 약점 6건(방향 반전 미이해 FP 등)은 `ml/reports/misclassification_log.md`에 기록.

### 남은 리스크

- 모범 특약을 위험으로 판정하는 FP(방향 반전)는 사용자 신뢰 훼손 요인 — v1.5 1순위
- Supabase 미연동 (저장·히스토리·피드백 없음) — 7주차
- PWA(vite-plugin-pwa)·Lighthouse 점검 — 7주차 다듬기에서

## 4주차 — FastAPI 모델 서버 + OCR 파이프라인 + 조항 분리 (2026-07-13)

### 문제

학습된 모델을 실제 요청을 받는 서비스로 만들어야 한다. 특히 (1) threshold·uncertain
정책을 추론 경로에 정확히 반영하고, (2) OCR→분리→분석 흐름에서 "교정 전 텍스트로
분석하지 않는다"(스펙 §9-4)는 안전장치를 지켜야 한다.

### 목표

`POST /analyze`(조항 분리→분류), `POST /ocr`(CLOVA), `GET /health`·`/model-info` 동작 (스펙 §8)

### 구현

- `model-server/app/`: segmentation(번호·문장 경계 분리), inference(모델 로드 1회,
  threshold 0.7 → `uncertain` 강등, 원 판정·확신도 동반 반환), patterns(가이드라인 기반
  위험 신호 14종 → reason 필드), main(엔드포인트 + 법률 자문 아님 고지)
- CLOVA General OCR 연동: base64/URL 입력, lineBreak 기반 줄바꿈 복원(세그멘테이션
  신호), `enableTableDetection=False`로 표 추출 과금 차단
- Dockerfile (Cloud Run PORT 대응), 모델 아티팩트는 이미지에 포함하는 단순 구성

### 의사결정

| 결정 | 이유 |
|---|---|
| `uncertain`은 강등이되 원 판정(`model_risk`)·확신도 동반 반환 | UI가 "모델은 caution으로 봤지만 확신 낮음"의 맥락을 보여줄 수 있게 |
| reason 필드를 모델과 독립된 규칙 신호로 | E2E 검증에서 모델이 놓친 danger(보증금 타인 종속)를 패턴 신호가 잡음 — 이중 안전망으로 UI에 함께 노출 |
| /ocr 결과를 바로 분석하지 않음 | 교정 강제(스펙 §9-4). /ocr은 텍스트+분리 초안만 반환, /analyze는 교정된 텍스트만 수신 |
| OCR은 CLOVA General 글자 추출만 | 월 100건 무료, 초과 3원/건. 표 추출(22원) 옵션 차단 |

### 검증

- /analyze E2E (샘플 특약 6조항): 4건 정확, 원상복구 단독 조항 과잉 경보(danger — 보수
  방향), 보증금 타인 종속 하향(caution — 단 규칙 신호가 별도 감지). 3주차 약점과 일치.
- /ocr 실호출: 렌더링한 특약 이미지 → 텍스트 정확 추출(줄바꿈 보존) → 조항 3건 분리 성공.
- 연동 삽질 기록: VPC 콘솔의 수동 연동 URL은 사설 IP(10.x)로 외부 접근 불가 →
  API Gateway 이용 신청 + 자동 연동으로 공개 URL(`apigw.ntruss.com`) 확보로 해결.

### 남은 리스크

- Cloud Run 콜드 스타트(모델 ~900MB 로드) — 스펙 §14의 진행 표시 UX로 완화 예정, 배포 후 실측 필요
- Supabase JWT 검증 미구현 — 프론트 연동(5주차) 시 추가
- 원상복구 과잉 경보·보증금 종속 하향은 모델 한계로 v1.5 과제. UI에서 reason 신호 병행 표시로 완화

## 3주차 — Baseline 2종 + KLUE-RoBERTa 파인튜닝, 평가 (2026-07-12)

### 문제

분류 모델의 성능을 "감이 아니라 수치로" 보여야 한다. 동시에 34문장짜리 val/test라는
작은 평가셋에서 어떻게 신뢰할 수 있는 비교를 하는가가 실제 난관이었다.

### 목표

- Baseline 2종(규칙, TF-IDF+LR) 대비 파인튜닝 모델의 개선 폭 제시
- 1순위 지표: danger Recall (FN 최소화, 스펙 §5.3) / threshold(`확인 필요`) 정책 결정

### 구현

- `eval_utils.py`로 전 모델 공통 평가 기준 통일 (Macro-F1 + danger Recall + 혼동행렬)
- Baseline 1: 가이드라인 §2.1을 정규식으로 옮긴 규칙 분류기 / Baseline 2: TF-IDF+LR
- KLUE-RoBERTa: Colab 1차 학습 실패 → 진단 → 로컬 CPU 재학습(v2)으로 회복
- threshold 튜닝, 규칙 백스톱 하이브리드 실험, test 최종 개봉 (모두 `ml/reports/week3_results.md`)

### 의사결정

| 결정 | 이유 |
|---|---|
| 1차 학습 실패를 리포트에 그대로 기록 | 34문장 val의 macro-F1 단독으로 best 체크포인트 선택 → 과소학습 에폭이 채택된 실패. 진단-수정 과정이 결과 수치보다 중요한 기록 |
| best 선택 기준을 (Macro-F1 + danger Recall)/2로 | 서비스의 비용 구조(danger FN이 최악)를 모델 선택 단계까지 일관 적용 |
| danger 가중 손실 1.5배 | 같은 원칙의 손실 함수 적용 |
| 하이브리드(규칙 백스톱) 기각 | val 개입 0건 + 규칙을 val 오답에 맞춰 보강하는 것은 검증셋 누수 |
| threshold 0.7 | 상향해도 고확신 FN은 구제되지 않음을 수치로 확인 — 커버리지만 손실 |

### 검증 (test 개봉, 1회)

- 위험도: v2가 danger Recall 0.636으로 최고 (B1 0.455, B2 0.545), danger FN 4건으로 최소.
  단 Macro-F1은 0.462로 baseline 이하 — caution 클래스가 test에서 붕괴.
- 카테고리: Macro-F1 0.967.
- val(0.749) → test(0.462) 간극의 원인: 클래스당 9~14건짜리 평가셋에서는 셋 구성의
  우연이 모델 실력보다 크게 작용. 프로토콜의 한계로 명시.

### 남은 리스크

- **위험도 모델의 caution 일반화 불안정** — 1주차 파일럿에서 확인한 safe/caution 경계의
  본질적 모호성이 모델 성능에도 그대로 나타남. danger 경계는 상대적으로 안정 (라벨과 동일 패턴).
- **평가셋 규모** — v1.5에서 희소 패턴 시드 보강 + 5-fold CV + 평가셋 확대로 전환.
- 모델 아티팩트는 git 미포함 (`model-server/models/`) — 재현은 `train_local.py` + 고정 시드.

## 2주차 — LLM 증강 + 전수 검수, train/val/test 분할 → dataset v1 (2026-07-12)

### 문제

시드 229문장만으로는 파인튜닝에 부족하다. LLM 증강으로 늘리되, (1) 증강문이 원본의
의미·위험도를 변질시키는 문제와 (2) val/test 시드의 패러프레이즈가 train에 흘러들어
평가가 오염되는 문제를 막아야 한다.

### 목표

- 층화 분할 70/15/15 (val/test는 시드 원본만)
- train 시드의 3배 증강 + 전수 검수 → `dataset v1`

### 구현

1. **분할 선행** (`split_dataset.py`): 21칸 층화 + largest remainder로 정확히
   70/15/15 (161/34/34), 고정 시드 42. 스펙 §5.2의 Step 순서(증강→분할)와 달리
   분할을 먼저 해 val/test 시드는 증강 대상에서 원천 배제.
2. **증강 7배치** (`aug_clauses.csv`): Claude가 배치당 50~80문장을 생성하고
   라벨러가 전량 검수(승인/수정/삭제)하는 사이클을 7회 반복 → 483문장 확정 (3.00x).
   변형 방법 6종 태깅(어순·용어·문체·축약·부연·구어체), 금지 규칙(금액·기한·범위
   변경, 긍/부정 반전, 주체 변경) 명문화.
3. **무결성 자동 검증** (`validate_aug.py`): 모든 증강문의 seed_id가 train에만
   속하는지(오염 차단), category/risk_level이 원본과 일치하는지(라벨 상속) 검사.
4. **병합** (`build_dataset.py`): 확정 라벨만 포함하는 원칙으로
   `dataset_v1/{train,val,test}.csv` 생성.

### 의사결정

| 결정 | 이유 |
|---|---|
| 분할을 증강보다 먼저 | val/test 문장의 패러프레이즈가 train에 들어가면 평가 지표가 낙관적으로 왜곡됨. 스펙 "증강은 train에만" 원칙의 안전한 구현 순서 |
| 배치 단위 생성-검수 사이클 | 1차 배치 검수에서 발견된 문제(함체, 어색한 축약)를 다음 배치 생성 규칙에 즉시 반영 — 대량 생성 후 일괄 검수보다 재작업이 적음 |
| danger 시드에 변형 집중 (3~4개) | False Negative 최소화 목표상 위험 조항의 표현 다양성이 가장 중요. 최종 train 분포가 danger 230건으로 최다 클래스가 됨 |
| 확정 라벨만 데이터셋 포함 | 미검수(provisional) 시드 1건(id 229)은 제외하고, 확정 시 재빌드로 포함 |

### 검증

- 증강 검수 결과: 생성 486건 중 483건 확정 (삭제 3 — 구성요소 누락 축약 1, 법률 해설투 1, 초기 중복 1), 표현 수정 5건
- validate_aug가 검수 중 변경된 시드 라벨의 상속 누락 3건을 자동 검출 (id 96, 102, 199) — 오염 방지 장치가 실제 작동함을 확인
- dataset v1: train 643 (safe 203 / caution 210 / danger 230), val 34, test 34 — 총 711문장

### 남은 리스크

- **증강문 생성자와 시드 작성자가 동일 모델(Claude)**: 문체 다양성이 한 모델의 분포에
  갇힐 수 있음. 사람 검수로 완화했으나, v1.5 재학습 루프에서 실사용 데이터(OCR 교정,
  피드백)로 분포를 넓히는 것이 근본 해결책.
- **val/test가 34문장씩으로 작음**: 클래스별로는 9~14건이라 지표의 신뢰구간이 넓다.
  3주차 평가에서 점추정치와 함께 이 한계를 명시하고, 시드가 늘면 재분할 검토.
- 시드 id 229 미확정 1건 — 확정 후 `build_dataset.py` 재실행으로 포함.

## 1주차 — 시드 데이터 수집, 라벨 체계·가이드라인 확정 (2026-07-11 ~ 07-12)

### 문제

공개된 "임대차 특약 위험도 라벨 데이터셋"이 존재하지 않는다. 분류 모델을 학습하려면
데이터를 직접 구축해야 하는데, 무작정 수집하면 (1) 특정 카테고리·클래스 편중,
(2) 라벨러(비전문가 1인)의 판단 기준 동요라는 두 가지 함정이 있다.

### 목표

- 시드 400+ 문장 (7 카테고리 × 3 위험도 = 21칸의 커버리지 관리)
- `labeling-guideline.md` 확정 — 비전문가도 일관되게 적용 가능한 판정 절차
- 자기 일치도 검증으로 가이드라인의 안정성 입증

### 구현

1. **위험 패턴 유형표 먼저** (`risk-pattern-matrix.md`): 21칸 매트릭스에 대표 패턴과
   칸별 최소 수량(10)을 정의한 후 수집 시작. 커버리지는 `ml/scripts/coverage.py`로 자동 집계.
2. **출처별 4차 수집** (누적 228문장): 법무부 표준임대차계약서(safe 뼈대 25) →
   전세사기 예방 가이드·칼럼(권장 특약 safe / 독소조항 danger) → 커뮤니티 실사례 →
   직접 작성 변형(부족 칸 겨냥). 각 행에 출처·근거 패턴을 `source_note`로 기록.
3. **가이드라인 v0.1→v0.6**: 5단계 판정 절차(§2.1) + 경계 보조 규칙(§2.2) +
   경계 사례집 35건. 파일럿에서 발견된 불일치가 곧바로 규칙·사례가 되는 구조.
4. **파일럿 3회 + 본 라벨링**: 50문장씩 3회 자기 일치도 검증(총 150문장, 겹침 없음) 후
   222문장 전수 검수. LLM(Claude)이 잠정 라벨을 붙이고 라벨러가 최종 승인/수정하는
   LLM 보조 라벨링 방식.

### 의사결정

| 결정 | 이유 |
|---|---|

| 유형표·칸별 최소 수량 먼저, 수집은 그다음 | 클래스 불균형을 수집 단계에서 차단 (스펙 §14 리스크 대응) |

| 합격 기준을 이중 기준으로 개정 (전체 ≥85% AND danger 경계 ≥96%) | 3회 파일럿에서 전체 일치율이 88%에서 정체, 잔여 불일치는 전부 safe↔caution 회색지대. 서비스의 치명 오류는 danger를 놓치는 것(FN)이므로 danger 경계를 핵심 지표로 승격. 근거·한계는 가이드라인 §6.1에 문서화 |

### 검증

- 자기 일치도(위험도): 88% / 86% / 88% — 합산 87.3% (150문장)
- danger 경계 일치도: 98% / 98% / 96% — 합산 97.3%
- 카테고리 일치도: 96% / 96% / 94%
- 파일럿 불일치 19건 전량 판정·사례집 수록, 시드 재라벨 15건+ (모두 `confirmed` 이력 유지)
- 최종 시드: 228문장, 21칸 전부 10건 내외, 위험도 비율 safe 36% / caution 30% / danger 34%

### 남은 리스크

- **safe↔caution 라벨 노이즈 ~12%**: 경계의 본질적 모호성. 데이터셋 문서와 모델 평가에
  명시하고, 평가 1순위 지표는 `danger` Recall로 유지 (스펙 §5.3).
- **authored 비중이 높음** (약 70%): 실제 계약서 문체와의 분포 차이 가능성.
  2주차 증강 시 문체 다양화 + 이후 실사용 피드백 데이터로 보정 예정.
- **시드 228 vs 목표 400**: 2주차 LLM 증강(3~5배)을 감안하면 250~300 마감도 유효
  (스펙 §5.2). 증강 전 커뮤니티 실사례를 소량 보강할지 결정 필요.
- **라벨러 1인 체제**: 자기 일치도만 검증됨. 여력이 되면 지인 1인에게 소표본
  교차 라벨링을 받아 라벨러 간 일치도(IAA)를 측정하는 것이 이상적.
