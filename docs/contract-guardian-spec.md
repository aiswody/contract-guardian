## 1. 문제 정의

### 1.1 핵심 장면

부동산 사무실에서 계약서를 처음 받아보는 순간은 대부분 **계약 당일, 서명 직전**이다.

- 특약사항 6~7줄을 읽고 판단할 시간은 몇 분뿐이다.
- 옆에서 중개사는 "다 표준 문구예요"라고 말한다.
- 검색해볼 여유도, 변호사에게 물어볼 시간도 없다.
- "원상복구", "근저당", "제소전화해" 같은 용어의 의미와 위험성을 모른다.
- 더 위험한 것은 **있어야 할 조항이 빠진 경우**다. 없는 것은 눈에 보이지 않기 때문에 알아챌 방법 자체가 없다.

### 1.2 기존 대안의 한계

| 기존 대안 | 한계 |
|---|---|
| 내집스캔, 집체크 (매물/임대인 위험 분석) | 계약 **전** 집과 집주인을 검증. 계약 **당일** 눈앞의 문서는 다루지 않음 |
| 로폼비즈니스, 앨리비 (B2B 계약 검토) | 기업 법무팀 대상. 개인 임차인이 쓰기엔 비용·접근성 장벽 |
| 커뮤니티 질문 (부동산 카페 등) | 답변까지 수 시간~수 일. 계약 당일에는 무용 |
| 변호사 상담 | 비용 부담. 수천만 원 보증금 계약에 수십만 원 상담은 현실적으로 생략됨 |

### 1.3 목표

임차인이 계약서에 서명하기 전, **5분 안에** 아래 세 가지를 알 수 있게 한다.

1. 이 계약서의 특약 중 나에게 불리한 조항은 무엇인가
2. 있어야 하는데 빠진 조항은 무엇인가
3. 중개사/임대인에게 어떻게 수정을 요청하면 되는가

## 2. 해결 방향 — 문제에서 해결까지

| 단계 | 사용자 문제 | 제품 해결 | 구현 근거 |
|---|---|---|---|
| 인식 | 계약서가 종이/사진이라 분석 자체가 불가 | 촬영 업로드 → OCR → 조항 단위 자동 분리 | OCR 엔진 + 조항 세그멘테이션 로직 |
| 판별 | 어떤 특약이 위험한지 모름 | 조항별 `정상/주의/위험` 분류 + 카테고리 태깅 | **직접 파인튜닝한 KLUE-RoBERTa 분류 모델** |
| 누락 | 있어야 할 조항이 없는 것은 더 못 알아챔 | 표준임대차계약서·필수 특약 체크리스트 대비 누락 탐지 | 표준 조항 임베딩 매칭 |
| 이해 | "위험"이라고만 하면 뭘 해야 할지 모름 | 쉬운 설명 + 수정 요청 문구 제안 | LLM API (분류 결과와 근거를 컨텍스트로 전달) |

**설계 원칙: 판별은 학습 모델, 설명은 LLM.**
위험 판별은 일관성과 재현성이 중요하므로 직접 학습·평가한 분류 모델이 담당하고, LLM은 이미 내려진 판별 결과를 사용자 눈높이 언어로 풀어주는 역할만 한다. LLM이 위험 여부를 즉석에서 판단하게 하지 않는다.

## 3. 사용자 흐름

### 3.1 메인 플로우 (계약 당일 시나리오)

1. 로그인 없이 또는 간편 로그인 후 진입한다.
2. 계약서 사진을 촬영/업로드한다. (여러 장 가능 — 계약서 본문 + 특약 페이지)
3. 분석 진행 화면: OCR → 조항 분리 → 위험 분석 단계가 순서대로 표시된다.
4. 결과 화면에서 확인한다:
   - 종합 요약 카드: 위험 N건 / 주의 N건 / 누락 N건
   - 조항 리스트: 원문 그대로 + 위험도 색상(초록/노랑/빨강) + 카테고리 뱃지
   - 조항 탭 시 상세: 왜 이런 판정인지(패턴 근거) + 쉬운 설명 + 수정 요청 예시 문구
   - 누락 체크리스트: 표준 대비 빠진 필수 조항 목록
5. 결과를 저장하고, 필요 시 요약을 이미지/텍스트로 공유한다.

### 3.2 보조 플로우

- **히스토리**: 과거 분석한 계약서 목록과 결과를 다시 본다. (재계약 시 비교 용도)
- **필수 특약 가이드**: 분석 없이도 볼 수 있는 "계약 전 체크리스트" 정적 콘텐츠. (SEO/유입 목적)
- **피드백**: 조항 판정에 대해 "도움됨/판정이 이상함"을 남긴다. → 재학습 데이터로 축적

## 4. 주요 기능 (MVP 범위)

### 4.1 계약서 업로드 & OCR
- 이미지(jpg/png) 및 PDF 업로드
- 한국어 OCR로 텍스트 추출
- 추출 결과를 사용자가 직접 교정할 수 있는 편집 화면 제공 (OCR 오류 대비 — 잘못 읽힌 텍스트로 잘못된 분석을 하지 않기 위한 안전장치)

### 4.2 조항 자동 분리
- 특약사항 영역을 번호/줄바꿈/문장 경계 기준으로 조항 단위 분리
- 분리 결과도 사용자가 병합/분리 수정 가능

### 4.3 조항 위험 분류 (핵심 AI — 직접 학습)
- 각 조항에 대해 2가지 예측:
  - **위험도**: `정상 / 주의 / 위험` (3-class)
  - **카테고리**: `보증금 반환 / 수리·하자 / 원상복구 / 계약 해지·갱신 / 근저당·권리관계 / 관리비·공과금 / 기타` (7-class)
- 모델의 confidence가 임계값(예: 0.7) 미만이면 판정을 단정하지 않고 `확인 필요` 상태로 표시

### 4.4 누락 조항 탐지
- 필수 조항 마스터(표준임대차계약서 + 전세사기 예방 필수 특약 7종 기반)를 사전 정의
- 업로드된 계약서의 조항 임베딩과 필수 조항 임베딩의 유사도 매칭 → 임계값 미만이면 "누락 가능성"으로 표시
- 누락 항목마다 권장 특약 예시 문구 제공

### 4.5 쉬운 설명 & 수정 요청 문구 (LLM)
- 분류 모델의 판정 결과·카테고리·근거 패턴을 컨텍스트로 LLM에 전달
- 출력: (1) 왜 위험한지 2~3문장 설명, (2) 중개사에게 말할 수 있는 수정 요청 문구 1개
- LLM 출력에는 항상 "참고 정보이며 법률 자문이 아닙니다" 고지 포함

### 4.6 MVP 제외 범위 (v2 이후)
- 등기부등본 분석 (내집스캔/집체크 영역과 겹침 — 의도적으로 제외)
- 임대인 신용/권리관계 조회
- 계약서 자동 작성
- 스토어 배포 앱 (MVP는 PWA로 대응, v2에서 Capacitor로 확장 — §11.1 참고)
- 범위 제한 Q&A 챗봇 (2026-07-13 추가): 분석 결과·필수 특약 가이드·용어 사전 **안에서만**
  답하는 후속 질문 봇. 자유 대화로 위험 여부를 즉석 판별하는 형태는 설계 원칙(§2)과
  충돌하므로 금지 — LLM 쉬운 설명(§4.5) 인프라 안정화 후 검토

## 5. AI 파이프라인 상세

### 5.1 전체 흐름

```
계약서 이미지 업로드
  → OCR (한국어 텍스트 추출)
  → 조항 세그멘테이션 (rule-based)
  → [모델 A] 위험도 분류 (KLUE-RoBERTa 파인튜닝, 3-class)
  → [모델 A'] 카테고리 분류 (동일 백본, 7-class)
  → [모델 B] 누락 탐지 (문장 임베딩 유사도 매칭)
  → [LLM] 판정 결과 기반 설명·수정 문구 생성
  → 결과 저장 (Supabase)
```

### 5.2 데이터 구축 전략 (이 프로젝트의 핵심 스토리)

공개된 "임대차 특약 위험도 라벨 데이터셋"은 존재하지 않는다. 따라서 데이터셋을 직접 구축하며, 이 과정 자체를 포트폴리오의 중심에 둔다.

**Step 1 — 시드 데이터 수집 (목표 400~600문장)**
- 국토교통부 주택임대차표준계약서 조항 전문
- 법률 칼럼·전세사기 예방 가이드에 인용된 특약 예시 (위험/권장 사례)
- 부동산 커뮤니티에 공유된 실제 특약 문구 (개인정보 제거 후)
- 직접 작성: 위험 패턴 유형별 변형 문장

**Step 2 — 라벨 체계 정의 및 라벨링 가이드라인 문서화**
- `docs/labeling-guideline.md`에 각 위험도/카테고리의 판단 기준과 경계 사례를 명문화
- 예: "원상복구 범위를 '통상 마모 포함 전부'로 규정 → 위험", "원상복구 조항이 있으나 범위 미명시 → 주의"
- 동일 문장을 2회 라벨링(시차를 두고)해 자기 일치도 확인 → 가이드라인 보완

**Step 3 — LLM 기반 데이터 증강 (시드의 3~5배)**
- 시드 문장을 의미 보존 패러프레이즈로 변형 (어순, 존칭, 용어 변형)
- **증강 데이터는 반드시 전수 검수 후 train set에만 포함** (val/test는 시드 원본만 사용 — 평가 오염 방지)

**Step 4 — 분할**
- train / val / test = 70 / 15 / 15
- test set은 학습 전 과정에서 절대 참조하지 않음

### 5.3 모델 학습 계획

| 단계 | 내용 | 평가 |
|---|---|---|
| Baseline 1 | 키워드 규칙 기반 분류 (근저당, 원상복구 등 패턴 매칭) | 규칙만으로 어디까지 되는지 하한선 확인 |
| Baseline 2 | TF-IDF + Logistic Regression | 고전 ML 대비 개선 폭 측정 |
| Main | KLUE-RoBERTa-base 파인튜닝 (위험도 3-class) | Macro-F1, 클래스별 Recall |
| Main' | 동일 백본으로 카테고리 7-class | Macro-F1 |
| 개선 | 클래스 불균형 대응 (weighted loss), threshold 튜닝 | — |

**평가 기준의 핵심: `위험 → 정상` 오분류(False Negative)를 최소화한다.**
위험한 조항을 안전하다고 말하는 것이 이 서비스에서 가장 치명적인 오류다. 따라서 전체 정확도보다 `위험` 클래스의 Recall을 우선 지표로 삼고, 애매한 구간은 `확인 필요`로 넘기는 threshold 정책을 채택한다. (혼동 행렬과 함께 README에 명시)

### 5.4 OCR 선택

| 후보 | 장점 | 단점 |
|---|---|---|
| Naver CLOVA OCR | 한국어 문서 인식률 최상 | 유료 (무료 티어 소량) |
| Upstage Document OCR | 문서 특화, 인식률 높음 | 유료 |
| PaddleOCR (한국어 모델) | 무료, 셀프 호스팅 | 인식률 열세, 후처리 필요 |

→ **MVP: CLOVA OCR 무료 티어로 시작**, 비용 초과 시 PaddleOCR fallback. OCR 결과 사용자 교정 화면이 있으므로 인식률 열세를 UX로 보완 가능.

### 5.5 재학습 루프 (v1.5 목표)

- 사용자 피드백("판정이 이상함") + OCR 교정 데이터가 쌓이면 검수 후 학습 데이터에 편입
- 모델 버전 관리: 분석 결과에 `model_version` 기록 → 버전별 성능 비교 가능
- 재학습 → 평가 → 배포 절차를 스크립트화 (`scripts/retrain.py`)

## 6. 아키텍처

```
Web (React + Vite, PWA)  ← Vercel 배포
  |
  |-- Supabase
  |     |-- Auth (이메일 / 카카오 OAuth)
  |     |-- PostgreSQL + RLS
  |     |     |-- profiles
  |     |     |-- contracts
  |     |     |-- clauses
  |     |     |-- standard_clauses
  |     |     |-- missing_checks
  |     |     |-- feedback
  |     |-- Storage (계약서 이미지 — 비공개 버킷)
  |
  |-- FastAPI 모델 서버  ← Docker, Cloud Run(또는 Railway) 배포
        |-- POST /analyze : OCR → 조항 분리 → 분류 → 누락 탐지
        |-- 분류 모델 (KLUE-RoBERTa, HuggingFace)
        |-- 임베딩 매칭 (sentence-transformers)
        |-- LLM API 호출 (설명 생성, 서버에서만 — 키 노출 방지)
```

**역할 분리 이유**: Supabase는 데이터·인증·권한(RLS)을, FastAPI는 무거운 추론을 담당. 모델 서버를 분리하면 모델 교체·재배포가 프론트와 독립적으로 가능하다.

## 7. 데이터베이스 설계

```sql
-- 사용자 프로필
profiles (
  id uuid PK (= auth.users.id),
  nickname text,
  created_at timestamptz
)

-- 계약서 분석 세션
contracts (
  id uuid PK,
  user_id uuid FK → profiles (nullable — 비로그인 체험 허용),
  title text,                      -- "OO빌 원룸 전세" (사용자 입력)
  contract_type text,              -- 'jeonse' | 'monthly'
  image_paths text[],              -- Storage 경로
  ocr_text text,                   -- 교정 반영된 최종 텍스트
  status text,                     -- 'uploaded' | 'analyzing' | 'done' | 'failed'
  model_version text,
  created_at timestamptz
)

-- 조항 분석 결과 (contracts 1:N clauses)
clauses (
  id uuid PK,
  contract_id uuid FK → contracts,
  order_index int,
  text text,                       -- 조항 원문
  category text,                   -- 7종 카테고리
  risk_level text,                 -- 'safe' | 'caution' | 'danger' | 'uncertain'
  confidence float,
  reason text,                     -- 판정 근거 패턴 요약
  explanation text,                -- LLM 생성 설명 (캐시)
  suggestion text                  -- LLM 생성 수정 요청 문구 (캐시)
)

-- 필수 조항 마스터 (관리자 시딩)
standard_clauses (
  id uuid PK,
  name text,                       -- "근저당 추가 설정 금지"
  description text,
  recommended_text text,           -- 권장 특약 예시 문구
  embedding vector(768)            -- pgvector
)

-- 누락 탐지 결과 (contracts N:M standard_clauses)
missing_checks (
  contract_id uuid FK,
  standard_clause_id uuid FK,
  is_present boolean,
  similarity float,
  PRIMARY KEY (contract_id, standard_clause_id)
)

-- 판정 피드백 (재학습 데이터원)
feedback (
  id uuid PK,
  clause_id uuid FK → clauses,
  user_id uuid FK,
  verdict text,                    -- 'helpful' | 'wrong'
  comment text,
  created_at timestamptz
)
```

**RLS 원칙**
- `contracts`, `clauses`, `feedback`: 본인 소유 데이터만 조회/생성
- `standard_clauses`: 전체 읽기 전용, 쓰기는 service role만
- 계약서 이미지 버킷: 비공개, 소유자만 signed URL 접근
- 계약서는 민감 문서이므로 "분석 후 원본 이미지 자동 삭제" 옵션 제공 (개인정보 최소 보관 원칙)

## 8. API 설계 (FastAPI)

```
POST /analyze
  body: { contract_id, ocr_text | image_urls }
  1) (이미지인 경우) OCR 수행
  2) 조항 세그멘테이션
  3) 조항별 위험도/카테고리 분류
  4) 필수 조항 매칭 → 누락 목록
  5) 위험/주의 조항에 대해 LLM 설명 생성
  return: { clauses[], missing[], summary }

POST /ocr
  body: { image_urls }             -- OCR만 먼저 수행 (교정 화면용)
  return: { text, segments[] }

GET /health, GET /model-info       -- 모델 버전/지표 노출
```

인증: Supabase JWT를 FastAPI에서 검증 (Wodylog·GHG에서 사용한 JWT 검증 패턴 재사용).

## 9. 정확도·안전을 위한 제약

1. **법률 자문 아님 고지**: 모든 결과 화면 상단 + LLM 출력 말미에 고정 고지. "위험" 대신 "불리할 수 있는 조항"이라는 표현 사용.
2. **불확실하면 단정하지 않는다**: confidence 임계값 미만은 `확인 필요`로 표시하고 전문가(무료 법률구조공단 등) 안내 링크 제공.
3. **False Negative 최소화 우선**: 평가·threshold 정책 전반에서 위험 조항을 놓치지 않는 방향으로 보수적으로 설계.
4. **OCR 오류 방어**: 분석 전 사용자 교정 단계를 강제 노출. 잘못 읽힌 텍스트로 분석하지 않는다.
5. **LLM 역할 제한**: LLM은 판별하지 않고 설명만 한다. 판별 결과와 다른 내용을 생성하지 않도록 프롬프트에서 판정 결과를 고정 컨텍스트로 제공.
6. **개인정보**: 이미지 비공개 버킷 + 자동 삭제 옵션 + 이름/주민번호 영역 마스킹 안내.

## 10. 기술적 의사결정 요약

| 결정 | 선택 | 이유 |
|---|---|---|
| 위험 판별 방식 | 직접 파인튜닝한 분류 모델 | 일관성·재현성·평가 가능성. LLM 판별은 같은 입력에 다른 답을 낼 수 있고 성능을 정량 평가하기 어려움 |
| 설명 생성 | LLM API | 자연스러운 눈높이 설명은 생성 모델이 우위. 단 판별 결과를 고정 컨텍스트로 제한 |
| 백본 모델 | KLUE-RoBERTa-base | 한국어 이해 성능 검증됨, base 사이즈로 무료 GPU(Colab)에서 학습 가능 |
| 데이터 | 직접 구축 + LLM 증강 + 전수 검수 | 공개 데이터셋 부재. 증강 데이터는 train에만 사용해 평가 오염 방지 |
| 모델 서버 분리 | FastAPI + Docker | 모델 교체/재배포를 프론트와 독립적으로. Supabase Edge Function은 무거운 추론에 부적합 |
| DB/인증 | Supabase (RLS + pgvector) | Wodylog에서 검증한 스택. 누락 탐지용 벡터 검색까지 한 곳에서 해결 |
| 누락 탐지 | 임베딩 유사도 매칭 | 분류가 아니라 "존재 여부" 문제이므로 생성/분류보다 검색이 적합 |
| 애매한 판정 | `확인 필요` fallback | 오답의 비용이 큰 도메인. 모르는 것을 아는 척하지 않는 설계 |

## 13. 포트폴리오 포인트

1. 공개 데이터셋이 없는 도메인에서 **데이터 구축(수집→라벨 체계→증강→검수)부터 시작한 ML 풀사이클**
2. "판별은 학습 모델, 설명은 LLM"이라는 **역할 분리 설계**와 그 이유
3. False Negative 비용이 큰 도메인에서의 **보수적 threshold·fallback 설계**
4. Baseline 2종 대비 파인튜닝 모델의 **정량적 개선 폭 제시** (감이 아니라 수치로)
5. Supabase RLS + 비공개 Storage + 자동 삭제로 **민감 문서 개인정보 보호 설계**
6. 기존 서비스(매물 검증/B2B 검토)와의 **명확한 포지셔닝 차별화**
